# KDT website: agent guide

Next.js (App Router) site backed by Supabase and deployed on Vercel. Setup, scripts, project layout, and env vars are in the [README](./README.md).

## Safety

- **Confirm with the user** before running destructive or irreversible commands (`git reset --hard`, `git clean -fd`, force push, mass file deletes, removing core deps).
- Never commit `.env*` files.

## Keeping docs current

If a change makes the README or this file wrong (renamed or moved files, new folders, scripts, env vars, routes, tables), fix the doc in the same PR.

## Package manager

- Use **pnpm** only. CI installs with `pnpm install --frozen-lockfile`.
- `package-lock.json` is still in the repo. Don't run npm or yarn, and don't update it.

## Pull requests and commits

Use conventional commit titles, matching the history on `main`:

```text
action(scope): short description
```

- `action`: `feat`, `fix`, `docs`, `style`, `refactor`, `chore`, or `ci`.
- `scope` is optional (e.g. `chore(deps): update packages`). Add the issue number (`#12`) when there is one.
- Imperative, lowercase start, no trailing period.

## Code quality

Run these before opening a PR. CI runs the first two on every push and PR:

```bash
pnpm format:check   # or pnpm format to fix
pnpm lint
pnpm exec tsc --noEmit
```

Prettier handles quotes (single, including JSX), line width (90), import order, and Tailwind class order. Don't format by hand.

## Imports, types, and barrels

- Path alias `@/` maps to the repo root. Use it for every non-relative import.
- Import through the folder barrels: `@/components/ui`, `@/components`, `@/hooks`, `@/contexts`, `@/lib`, `@/lib/data`, `@/types`, `@/utils`.
- When you add a module, export it from its folder's `index.ts`. Each action folder (`components/SponsorActions/`, …) has its own `index.ts`.
- Shared types go in `types/type.ts`, not in components or route files. Name a type after what it is, without shadowing DOM globals (`ClubEvent`, not `Event`).

## File names and folders

- shadcn components keep their CLI names (`components/ui/alert-dialog.tsx`). shadcn's `hooks/use-mobile.ts` keeps its name too.
- Our own components, providers, and contexts use PascalCase matching the export (`components/Navbar.tsx`, `contexts/AuthContext.tsx`).
- Hooks use camelCase matching the hook (`hooks/useAuth.ts`).
- Admin actions for a section live in `components/<Section>Actions/` as `AddEdit.tsx` and `Delete.tsx` (plus `Reorder.tsx` where needed).
- Route folders under `app/` are lowercase, since they become the URL. Page metadata goes in the route's `layout.tsx`.
- `lib/` holds clients and service helpers (`supabase.ts`, `rubric.ts`) and `lib/data/` holds fallback and static content. `utils/` holds pure helpers (dates, animations, icon map).

## UI: shadcn and Lucide

- Every shadcn component is installed in `components/ui/`. Check there and the [shadcn docs](https://ui.shadcn.com/docs/components) before building common UI (alerts, toasts, empty states, form fields, skeletons). Don't reimplement them.
- **Don't edit `components/ui/`.** It's generated by the shadcn CLI (and ignored by ESLint). Update a component with `pnpm dlx shadcn@latest add <component> --overwrite`.
- The theme (`radix-luma`, zinc base, tokens in `app/App.css`) is the design system. Use components as-is: pick a `variant` or `size` prop instead of restyling with `className`, and use theme tokens (`bg-destructive`, `text-muted-foreground`) instead of raw palette colors (`bg-red-500`, `text-white`).
- Layout classes around components (flex, grid, gaps, container widths) are fine. Override a component's own styling only for a real usability need, and say why in the PR.
- Icons come from `lucide-react`. Inside a shadcn component (`Button`, `Badge`, …) don't size the icon (`size={20}`, `className='h-4 w-4'`); the component does that.
- Calls to action get an icon before the label (`<Button><ListPlus /> Add sponsor</Button>`). Cancel and close buttons don't need one. Icon-only buttons need an `aria-label`.
- Some older components predate these rules (raw colors, sized icons, `Loader2` spinners). Don't copy those patterns into new code; fix them in a file you're already changing.

## States and feedback

- **Loading:** use `<Spinner />` from `@/components/ui`, including inside a pending submit button. Don't use `Loader2 className='animate-spin'` or plain "Loading…" text.
- **Empty:** show an empty state instead of a blank section (e.g. "No upcoming events"). Sections with bundled fallback data in `lib/data/` show that instead.
- **Errors:** inline `Alert` for a section that failed to load, toast for a failed action.
- **Toasts:** use `const { toast } = useToast()` from `@/hooks`, not `sonner` directly.
- **Destructive actions** confirm through an `AlertDialog` that names the item, as the `*Actions/Delete.tsx` dialogs do.

## Forms

- Validate with **Zod** + **React Hook Form** + `zodResolver`, rendered with the shadcn `Form` components so errors show under the field (`FormMessage`), not in an alert.
- One-off schemas sit next to the form. Shared ones go with the types.
- Disable the submit button while it's pending.

## State and data

- Shared client state uses **context + hooks**: the provider in `contexts/`, and a hook in `hooks/` that throws when used outside the provider (see `useAuth`, `useToast`).
- Components that use state, effects, or browser APIs start with `'use client'`.
- Supabase reads and writes use the shared anon client from `@/lib`. Don't create another client in the app.
- External APIs (Rubric) are called only from route handlers in `app/api/`, through the helpers in `lib/rubric.ts`, which cache responses. Components fetch the internal route (`/api/club`), never the external host.
- Route handlers return `Response.json(...)`. On failure, log the error with `console.error` and return a short user-facing message with a status code (`{ error: 'Failed to load club data' }`, 500). Don't put exception text in the response.

## Database (Supabase)

- The browser uses the **anon key**, so Row Level Security is the only thing protecting the data. Every new table enables RLS and adds its policies in the same migration (public read, authenticated write, as the existing tables do).
- Create every migration with the Supabase CLI: `supabase migration new <name>` (e.g. `link_scheduled_at`). It writes the timestamped file in `supabase/migrations/`. Never create the file or write its timestamp by hand. Never edit a migration that has already been applied.
- The service-role key is only for `scripts/` (read from `.env`). Never give it a `NEXT_PUBLIC_` name or import it into app code.
- When a column changes, update its type in `types/type.ts` in the same PR.

## Styling

- **Tailwind CSS v4** only, configured in `app/App.css` (`@import 'tailwindcss'`, `@plugin`, `@custom-variant`). Don't add a `tailwind.config.js`.
- Reuse the existing utility classes in `App.css` (`t200e`, `fade-in`, `glass`, …) before adding new ones. Don't add CSS modules.
